# Atlas Unreal Cross-Process Render Recovery Contract v1

**Status:** Implementation authority for the next Unreal recovery milestone  
**Scope:** Unreal 5.6 render execution, durable job identity, crash/restart reconciliation, evidence, receipts, and production-artifact lineage  
**Authority:** Atlas-owned execution/recovery contracts  
**Supersedes:** Hermes' pre-red-team recovery proposal where this document differs

---

## 1. Purpose

This contract defines the minimum safe architecture for making Atlas Unreal render jobs recoverable across Atlas and Unreal process boundaries without weakening the existing authorization, evidence, receipt, or provenance guarantees.

The current Stage 17 live proof is already established against real Unreal Engine 5.6. This contract extends that proven boundary; it does not replace it.

The target is:

```text
Atlas authorized intent
    -> durable execution record
    -> controlled Unreal execution
    -> durable engine execution witness
    -> restart/reconciliation
    -> independent evidence verification
    -> immutable receipt
    -> production-artifact manifest
    -> exact lineage verification
```

---

## 2. Non-Negotiable Authority Boundary

The authority model is fixed:

```text
Qwen / AI
    -> reason and propose structured production intent

Atlas Python / Controller
    -> validate
    -> resolve
    -> authorize
    -> execute
    -> track
    -> verify
    -> recover

Unreal
    -> controlled execution worker
    -> reports raw execution observations

Independent verification
    -> establishes what actually happened
```

No recovery implementation may introduce:

- a second authorization system in Unreal;
- a second scheduler in Unreal;
- a second recovery authority in Unreal;
- model-controlled authorization;
- silent mutation of an authorized production plan;
- automatic resubmission when prior execution remains uncertain.

Unreal journaling is **execution evidence only**. Its journal does not authorize, schedule, retry, or adjudicate recovery.

---

## 3. Core Recovery Principle

The following rule is absolute:

> A durable Atlas job record is evidence of recorded intent and authorization lineage. It is not proof that Unreal accepted, started, or completed the render.

Therefore:

- Atlas MUST NOT synthesize `finished`, `success`, or `failed` engine terminal flags.
- Files existing on disk MUST NOT by themselves create a successful Unreal execution claim.
- Receipt issuance MUST remain downstream of independently verified execution evidence.
- Uncertainty MUST stop successful provenance; it MUST NOT create execution authority.

---

## 4. Job Identity

### 4.1 Root identity

`atlas_job_id` is generated by Atlas before submission and is immutable for the lifetime of one authorized execution attempt.

A root job ID MUST NOT be supplied by a model.

The ID MUST be validated before use in any filesystem path.

### 4.2 Attempt identity

A re-authorized rerender is a new execution attempt. It MUST have:

- `attempt_ordinal`;
- the new authorization binding required by the existing Atlas authorization system;
- a new isolated output namespace;
- a new immutable `atlas_job_id`.

For v1, the preferred identity rule is:

```text
atlas_job_id = Atlas-generated cryptographically random UUID
```

The durable record is the source that preserves the identity across restarts. Recovery MUST reuse the existing persisted ID rather than regenerate one.

`attempt_ordinal` distinguishes authorized attempts; it does not authorize retries by itself.

### 4.3 Filesystem safety

`atlas_job_id` MUST match a strict canonical identifier format and MUST never be interpreted as a path fragment without validation.

The record filename stem MUST equal the interior `atlas_job_id`.

Atlas MUST persist a structured, versioned `AtlasRenderJobRecord` before sending `submit_render`.

Minimum fields:

```text

atlas_job_id

authorization_id
canonical_digital_twin_id
sequence_asset_path

config_digest
output_parent_directory
output_directory

recovery_status

atlas_submitted_at

origin_editor_session_id

last_observed_revision

```

The record MUST distinguish:

- **authoritative fields** — Atlas-resolved/authorized identity and plan;
- **observed fields** — facts received from Unreal/independent inspection;
- **derived fields** — values computed from authoritative inputs;
- **operational fields** — timestamps, recovery bookkeeping, and references.

No model may write or modify authoritative identity, lifecycle, evidence, artifact, or recovery fields.

## 6. Durable Store

`AtlasRenderJobStore` MUST use versioned, fail-closed persistence.

Atomic replacement alone is not treated as a universal power-loss proof on Windows.

The store MUST provide:

1. atomic record replacement;
2. explicit corruption detection;
3. record digest validation;
4. exclusive per-job write ownership;
5. single-coordinator ownership for the store;
6. create/load/update semantics that reject stale writers;
7. non-destructive handling of corrupt or quarantined records.

A record whose authoritative digest fails MUST NOT be treated as merely absent or orphaned. It MUST enter a distinct corruption state requiring gate adjudication.

---

## 7. Submission Ordering

The required ordering is:

```text
existing valid authorization
    -> resolve exact production plan
    -> compute request/config digests
    -> compute job-scoped output directory
    -> persist durable job intent
    -> acquire exclusive Atlas execution claim
    -> verify Unreal recovery capability
    -> submit_render with atlas_job_id
    -> bind returned unreal_job_id/session identity
    -> track
```

A transport timeout, disconnect, or lost response after a submission attempt MUST be classified as **acceptance unknown** unless Atlas has an authoritative rejection.

Acceptance unknown MUST NOT trigger a blind resubmission.

Atlas MUST reconcile before deciding whether any further execution is permitted.

A submission record MUST never be silently discarded merely because no immediate Unreal response was observed.

---

## 8. Atlas-Side Duplicate Execution Protection

Atlas owns the primary duplicate-execution invariant.

Before submission Atlas MUST acquire an exclusive claim for `atlas_job_id`.

Only one Atlas coordinator may own the render-job store at a time.

Per-job ownership MUST remain exclusive for the non-terminal lifetime of the execution attempt.

Unreal-side duplicate suppression remains defense in depth.

A terminal Atlas job MUST be rejected at the Atlas submit gate. Unreal journal replay MUST never be interpreted as permission to execute again.

No automatic render retry is permitted while prior execution remains uncertain.

---

## 9. Unreal Process Identity

The system MUST distinguish:

1. Atlas job identity;
2. Unreal job identity;
3. Unreal process-incarnation identity;
4. transport responder identity.

`editor_session_id` MUST identify one Unreal process incarnation and MUST be freshly generated for every process start.

It MUST NOT rely on a reusable application session identifier alone.

The durable identity tuple MUST include at least:

```text
editor_session_id
process_id
process_creation_time
project_identity
engine_version
```

PID is diagnostic, not sufficient identity.

A session mismatch means **different responder/process incarnation**. It does not by itself prove that the previous process has terminated.

Recovery MUST NOT treat a new Unreal session as proof that an old hung process is dead.

### Process Supervision and Deployment Modes

Parent PID death alone is INSUFFICIENT proof of process-tree quiescence on Windows. When an engine process terminates or crashes, descendant worker processes (e.g. `ShaderCompileWorker.exe`, `UnrealPak.exe`, `CrashReportClient.exe`, or custom commandlets) are NOT terminated by the OS and are NOT re-parented; their parent PID references become stale integer identifiers subject to OS recycling.

Atlas therefore establishes two explicit deployment modes:

1. `CONTAINED_JOB_OBJECT` (Autonomous Recovery Mode):
   - Unreal is launched under Atlas-controlled process supervision within a Windows Job Object.
   - The Job Object MUST be configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and silent breakaway MUST be prohibited (`JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` disabled, explicit `CREATE_BREAKAWAY_FROM_JOB` disallowed).
   - Quiescence requires:
     ```text
     JobObjectHandleValid == TRUE AND QueryInformationJobObject(BasicAccounting).ActiveProcesses == 0
     ```
   - Only when `ActiveProcesses == 0` is confirmed may recovery inspect or adopt terminal disk artifacts.

2. `UNCONTAINED_ATTACHED` (Interactive Development Mode):
   - Atlas connects over the named pipe to an already-running, externally launched Unreal process without Job Object containment.
   - In this mode, cross-process artifact recovery and adoption across process restarts is STRICTLY UNSUPPORTED and FAILS CLOSED.
   - If the engine process terminates, disconnects, or crashes while a job is non-terminal, recovery MUST NOT assume parent PID death proves descendant quiescence. Recovery blocks in `WAITING_FOR_ENGINE_QUIESCENCE` until the execution deadline, then transitions to `RECOVERY_FAILED`. It NEVER inspects or adopts artifacts.

## 10. Engine Journal

The Unreal journal is a durable **witness record**, not an authority system.

It MUST be stored in an Atlas-designated durable location outside the project's disposable `Saved/` tree:

```text
<ProjectDir>/AtlasWitnessJournal/<atlas_job_id>__<unreal_job_id>.json
```

The journal MUST retain execution history and MUST NOT overwrite a previous execution identity.

Recommended logical key:

```text
(atlas_job_id, unreal_job_id)
```

### Per-Attempt Nonce and Witness Authentication

To prevent replayed, restored, or cross-attempt witness journals from being accepted as valid evidence, Atlas generates a cryptographically unpredictable 256-bit `attempt_nonce` (`secrets.token_hex(32)`) prior to submission.

- The `attempt_nonce` is generated and controlled solely by Atlas.
- The `attempt_nonce` MUST be persisted in the durable `AtlasRenderJobRecord` under operational intent before any transport transmission.
- The `attempt_nonce` is transmitted to Unreal in `submit_render` arguments (`arguments.attempt_nonce`).
- Unreal consumes the nonce strictly as the secret key for witness HMAC calculation; Unreal NEVER creates or authorizes the nonce.
- **Secret Handling Invariant:** The secret `attempt_nonce` itself MUST NEVER be serialized as plaintext into journal files, receipts, manifests, or normal diagnostic logs.

### Canonical Journal Attestation

Each journal entry phase MUST be authenticated via HMAC-SHA256:

```text
entry_digest = HMAC-SHA256(
    key = UTF8(attempt_nonce),
    message = UTF8(canonical_journal_payload)
)
```

The canonical journal payload MUST include:

```text
schema_version
atlas_job_id
unreal_job_id
attempt_ordinal
phase
phase_sequence
editor_session_id
process_creation_time_utc
output_directory
output_manifest   # required on FINISHED
```

Journal entries MUST be self-describing and contain at least:

```text
journal_schema_version
atlas_job_id
unreal_job_id
attempt_ordinal
phase
phase_sequence
state_source
editor_session_id
process_id
process_creation_time
sequence_asset_path
config_digest
authorization_id
output_directory
expected_output_spec
written_at
entry_digest
output_manifest   # required on FINISHED
```

Required phases and monotonic sequence order:

```text
ACCEPTED (phase_sequence = 1)
STARTED  (phase_sequence = 2)
FINISHED (phase_sequence = 3)
FAILED   (phase_sequence = 3, if failed)
```

`phase_sequence` MUST be strictly monotonically increasing. Earlier phase entries MUST NOT be overwritten or truncated; the journal maintains an append-only `phase_history` list.

`ACCEPTED` MUST be durably written before MRQ execution is dispatched.

If `ACCEPTED` cannot be durably recorded, no MRQ job may be allocated.

`FINISHED` MUST be written only from the authoritative terminalization path after the engine has completed production of the declared output set.

A missing, malformed, partial, or unreadable journal is **unknown state**, not evidence of absence. Any journal failing HMAC validation or phase sequence checks MUST be classified as `UNTRUSTED_WITNESS` and fail closed to `RECOVERY_FAILED`.

## 11. Journal Durability and Integrity

The journal writer MUST have explicit crash-consistency semantics.

The implementation MUST define behavior for:

- malformed/truncated entry;
- incomplete replacement;
- disk full;
- access denial;
- file lock/sharing violation;
- partial directory state;
- simultaneous process failure.

Each consumed journal entry MUST be validated structurally and cross-validated against the Atlas durable record.

Any mismatch in:

```text
atlas_job_id
authorization_id
sequence_asset_path
config_digest
output_directory
expected_output_spec
attempt identity
```

MUST fail closed.

An integrity digest is a consistency check, not proof of trusted origin. The system MUST therefore continue to compare the journal against Atlas-authoritative data.

---

## 12. Output Isolation

Every execution attempt MUST use an exclusive output namespace:

```text
<authorized_output_parent>/<atlas_job_id>/
```

Atlas computes this location. A model and Unreal cannot choose the job identity or output isolation.

The computed path MUST be included in the authorized request/config digest before submission.

No two execution attempts may share an output directory.

This structural isolation is the primary defense against artifact misattribution.

---

## 13. Artifact Attestation

A successful terminal Unreal observation MUST include an engine-attested output manifest.

Each file entry MUST include at least:

```text
path
size
sha256
```

The engine SHOULD compute these values in its terminalization path.

Atlas MUST independently hash the bytes it reads from disk and require exact equality with the engine-attested hashes before accepting the artifact set.

Filename, count, path, and modification time are **cross-checks only**. They MUST NEVER be sufficient by themselves to establish execution identity.

`mtime` may reject suspicious state; it must not authorize adoption.

---

## 14. Artifact Completeness

Non-zero size and an image magic header are insufficient integrity checks.

For PNG output, v1 verification MUST establish container completeness, including:

- valid `IHDR`;
- valid chunk structure;
- valid chunk CRCs;
- terminal `IEND`;
- expected dimensions;
- exact expected output/frame topology.

Other formats MUST have format-specific validators.

Unknown or unsupported output topologies MUST fail closed.

Where feasible, the engine should use temporary output names followed by atomic rename to the final names, reducing the chance of Atlas inspecting a partially-written final artifact.

---

## 15. Evidence Source Classes

Evidence MUST distinguish execution observations by source.

Allowed classes:

```text
ENGINE_LIVE
ENGINE_JOURNAL_ATTESTED
```

`ENGINE_LIVE` is obtained from current Unreal inspection.

`ENGINE_JOURNAL_ATTESTED` is derived from a preserved, structurally valid Unreal journal observation.

Atlas MUST NOT construct a synthetic terminal Unreal observation from filesystem artifacts alone.

The existing authoritative `verify_render_job_evidence()` boundary MUST be extended only as necessary to validate these source classes and their identity bindings.

## 17. Receipt and Provenance Rules

The existing chain remains authoritative:

```text
engine observation
    -> independent evidence verification
    -> verified UnrealEvidence
    -> UnrealRenderReceipt
    -> ProductionArtifactManifest
    -> ProductionArtifactStore
    -> reload
    -> exact lineage verification
```

Receipt issuance MUST require `verified == True`.

The receipt store MUST be create-if-absent for `atlas_job_id`.

A second receipt for the same job MUST NOT replace the first.

Receipt digest inputs MUST be stable and exclude transient wall-clock/recovery bookkeeping values that would make a logically identical re-derivation produce a different seal.

On restart, if the receipt already exists, Atlas MUST reconcile the job record from the valid receipt rather than create a competing receipt.

---

## 18. Authorization Continuity

Recovery MUST preserve the original authorized execution binding.

For any **new execution** or execution-changing action, Atlas MUST revalidate through the existing authorization system that:

- the authorization exists;
- it is not revoked/expired;
- the requested sequence/twin/config remain within scope;
- the current operation is still authorized.

Historical verification of an execution that already completed may rely on the original valid authorization at acceptance time, provided the execution evidence is trustworthy and complete.

Authorization expiry/revocation MUST NOT be invented by the recovery layer as a reason to rewrite history. It MUST, however, block any new execution or unauthorized corrective action.

Recovery never accepts authorization values from a model.

---

## 19. Reconciliation Contract

`reconcile_render_jobs` MUST be a read-only engine observation operation.

It MUST expose the complete observable job catalog, not only IDs supplied by Atlas.

It MUST include:

```text
schema_version
engine_session_identity
journal_status
known execution records
live MRQ records
entry phase/state source
per-job identity and config bindings
output manifests where terminal
machine-readable error_code
```

Required `journal_status` values:

```text
COMPLETE
PARTIAL
UNREADABLE
```

Atlas MUST fail closed on `PARTIAL` or `UNREADABLE` for any decision requiring execution history.

An engine job with no matching Atlas record MUST be classified as `UNMANAGED_ROGUE` and excluded from artifact adoption. Atlas MUST NOT silently adopt or terminate it through recovery.

The reconcile operation MUST support pagination or equivalent bounded catalog retrieval.

### Bounded Wire Framing Protocol

To prevent transport truncation from masquerading as catalog absence, every `reconcile_render_jobs` wire payload MUST carry explicit framing fields:

```text
schema_version: int
request_id: str
catalog_generation: int
payload_byte_length: int
payload_sha256: str
complete: bool
records: list
```

Client transport implementations MUST:
1. Read the exact declared `payload_byte_length` bytes;
2. Verify `SHA256(received_payload_bytes) == payload_sha256`;
3. Validate that `complete == true`.

Any early stream termination, connection drop, byte count discrepancy, or SHA-256 digest mismatch MUST classify the entire catalog response as `UNREADABLE`. A truncated or unreadable response MUST NEVER be interpreted as "job absent" or "empty catalog". Bounded recovery queries SHOULD supply a `job_ids` filter to prevent named pipe buffer overflow.

## 20. Reconciliation Algorithm

For every non-terminal Atlas job:

### Step 1 — Durable integrity

Load the record and validate schema, identifier, authoritative digest, and legal lifecycle state.

Corruption is terminal `RECORD_CORRUPT` pending gate adjudication.

### Step 2 — Receipt/provenance probe

Check existing durable receipt/provenance stores first.

Probing the receipt store requires full identity matching across the 8 immutable fields:
1. `atlas_job_id`
2. `attempt_ordinal`
3. `authorization_id`
4. `canonical_digital_twin_id`
5. `sequence_asset_path`
6. `config_digest`
7. `output_directory`
8. `receipt_digest`

If a valid receipt matching all 8 fields exists, repair the job record from the receipt and do not execute again. Any receipt mismatch fails closed and is NOT adopted.

### Step 3 — Authorization continuity

For any action that would create new execution, revalidate current authorization through the existing authority.

### Step 4 — Engine capability/session handshake

Require a compatible wire schema and recovery-capable Unreal session.

### Step 5 — Catalog inspection

Request the complete engine catalog and journal status.

### Step 6 — Identity matching

Match candidates using exact bound identity:

```text
atlas_job_id
attempt identity
unreal_job_id, if already bound
origin editor session, where applicable
sequence_asset_path
config_digest
output_directory
expected output specification
```

Unambiguous matches may proceed.

Ambiguous matches MUST fail closed.

### Step 7 — Catalog→disk→catalog stability

For a terminal job whose artifact bytes are being inspected:

```text
catalog snapshot A
    -> disk inspection/hash verification
    -> catalog snapshot B
```

A material change between A and B invalidates the pass and returns the job to `RECOVERY_PENDING`.

### Step 8 — Evidence

Only preserved engine-live or engine-journal-attested execution observations may enter the authoritative evidence verifier.

### Step 9 — Finalization

Verified evidence may produce exactly one immutable receipt and one corresponding production-artifact lineage record.

## 21. Recovery Cases

### Case A — Current Unreal session contains the exact job

Proceed with normal inspection and verification.

### Case B — Prior session journal contains an exact terminal FINISHED record for a bound `unreal_job_id`

Use `ENGINE_JOURNAL_ATTESTED` evidence, verify hashes against the recorded output manifest, then continue normal receipt/provenance verification.

### Case C — No engine execution evidence; no attributable artifacts

Terminate safely as `ORPHANED` or `RECOVERY_FAILED` according to the authoritative state machine.

No receipt.

### Case D — No engine execution evidence; artifacts exist

**Never recover to VERIFIED/FINALIZED.**

Classify as:

```text
ORPHANED_ARTIFACTS_PRESENT
```

**Non-Mutation Invariant:**
Autonomous recovery MUST NOT move, rename, delete, overwrite, or adopt these artifacts.
Artifacts remain strictly untouched in place on disk. The coordinator only records the observation diagnostics and transitions the job record to `ORPHANED_ARTIFACTS_PRESENT` (terminal for autonomous recovery), escalating to a human operator. Physical quarantine or cleanup requires explicit separate operator authorization.

No synthetic `finished/success` state may be created.

### Case E — Atlas record and Unreal record disagree on bound identity

`RECOVERY_FAILED`.

### Case F — Config/sequence/output binding mismatch

`RECOVERY_FAILED`.

### Case G — Engine claims terminal success but independently verified artifact set is missing/invalid

`FAILED`.

### Case H — Multiple Unreal executions claim the same Atlas job

`RECOVERY_FAILED`.

All duplicate executions remain recorded; history MUST NOT be overwritten.

The engine witness MAY surface `journal_status="CONFLICT"` as the signal for this
duplicate-identity backstop: when the single-candidate reconcile catalog is built
keyed by `atlas_job_id` (the engine is defense-in-depth, never a second recovery
authority) and the engine detects that a same-`atlas_job_id` journal/in-memory
candidate carries a materially different execution identity (`unreal_job_id`,
`attempt_ordinal`, or `authorization_id`) before the idempotent collapse, it
reports `journal_status="CONFLICT"` and attaches structured `conflict_evidence` to
the surviving catalog entry without overwriting the original identity. Atlas maps
`journal_status="CONFLICT"` to Case H → `RECOVERY_FAILED` (no receipt, no retry,
no adoption, no synthetic success). This is distinct from `PARTIAL`/`UNREADABLE`
(Case J → `RECOVERY_PENDING`). The engine only reports the conflict; it never
decides which execution is authoritative.

### Case I — Journal is present but belongs to a prior/non-current session and the execution identity is not already bound

Do not treat it as a live job.

If the prior execution cannot be proven against the durable Atlas identity, fail closed.

### Case J — Journal is unreadable or partial

Treat as unknown, not absent.

Enter bounded `RECOVERY_PENDING`; after the defined deadline/budget, terminate as `RECOVERY_FAILED`.

## 22. Lifecycle State Machine

There MUST be one normative lifecycle enum shared by schema, validator, reconciliation, tests, and documentation.

Recommended v1 lifecycle states:

```text
PENDING_SUBMISSION
SUBMITTED
RENDERING
COMPLETED_UNVERIFIED
VERIFIED
FINALIZED
FAILED
ORPHANED
ORPHANED_ARTIFACTS_PRESENT
RECOVERY_FAILED
RECORD_CORRUPT
```

`WAITING_FOR_ENGINE` is a recovery status, not a lifecycle state.

Terminal states:

```text
FINALIZED
FAILED
ORPHANED
ORPHANED_ARTIFACTS_PRESENT
RECOVERY_FAILED
RECORD_CORRUPT
```

Terminal states MUST never regress.

`RECOVERY_PENDING` is likewise preferably represented as a `recovery_status` rather than a lifecycle state so transport unavailability does not accidentally mutate execution state.

No state transition may be implemented merely because a section of documentation names the state; the normative enum controls legality.

---

## 23. Recovery Budgets and Deadlines

Transport unavailability is not by itself evidence of execution failure and MUST NOT burn the ambiguity budget.

Recovery must have explicit deadlines.

The recovery budget SHOULD be consumed by conclusive ambiguity events such as:

- conflicting execution identities;
- unreadable/partial journal;
- authorization discontinuity;
- duplicate execution evidence.

A healthy render experiencing temporary transport loss MUST be allowed to remain recoverable until its execution/submission deadline is reached.

Recovery loops MUST be bounded.

No automatic render retry is permitted solely because a recovery attempt was exhausted.

---

## 24. Quarantine

Quarantine MUST be non-destructive.

The system must record:

```text
original path
quarantine path
reason
job identity
timestamp
authorization context
```

No recovery failure may delete artifacts merely to make the store appear clean.

Any new attempt after failure requires the existing authorized replanning/recovery gate and a new attempt identity/output namespace.

## 28. Shared Filesystem Boundary

Disk-based artifact reconciliation is valid only when Atlas and Unreal have a shared, verified filesystem view.

Before enabling disk reconciliation, Atlas MUST establish that the engine's configured output namespace maps to the same filesystem Atlas is inspecting.

If filesystem identity cannot be established, recovery MUST fail closed rather than inspect a potentially unrelated path.

For the current local Windows named-pipe deployment, co-location should be the default supported mode for recovery v1.

## 29. Concurrency Rules

The implementation MUST protect against:

- two Atlas coordinators;
- two Atlas reconciliation passes for one job;
- concurrent `submit_render` calls for one `atlas_job_id`;
- stale durable-record writers;
- receipt-issuance races;
- delayed/obsolete Unreal observations.

Required controls include:

- one coordinator lock;
- per-job ownership/lock or equivalent compare-and-swap;
- revision checks on durable record updates;
- idempotent create-if-absent receipt persistence;
- observation revision/request identity checks.

### Store-Gated Receipt Publication and Fencing

A stale coordinator MUST NOT be able to create a receipt or finalize an Atlas job after losing ownership. `O_CREAT | O_EXCL` alone is an insufficient fence because a partitioned coordinator holding a stale lease can win the filesystem race before its subsequent store update is rejected.

Receipt publication MUST be a store-gated atomic protocol:

```text
publish_verified_receipt(
    atlas_job_id,
    attempt_ordinal,
    presented_lease_token,
    expected_record_revision,
    receipt_payload
)
```

The store executes the following atomic sequence under exclusive lock:
1. Load current `AtlasRenderJobRecord`.
2. Verify `presented_lease_token > record.last_accepted_lease_token`.
3. Verify `record.record_revision == expected_record_revision`.
4. Verify `record.lifecycle_state` is eligible for finalization.
5. Atomically advance `record.last_accepted_lease_token = presented_lease_token` and flush to durable storage.
6. Create receipt file atomically using `O_CREAT | O_EXCL` at `<ReceiptStoreDir>/<atlas_job_id>__<attempt_ordinal>.json` embedding `presented_lease_token` and `coordinator_id`.
7. Update `AtlasRenderJobRecord` to `lifecycle_state = FINALIZED`, `recovery_status = RESOLVED`, advancing `record_revision` and writing atomically.

If a coordinator crashes after Step 6 but before Step 7:
On the subsequent recovery pass, the new coordinator discovers the fully durable, valid receipt via the Receipt-First probe (§20 Step 2). Because the receipt embeds the valid token and matches the job identity, the new coordinator safely repairs the record to `FINALIZED` without re-executing or issuing a competing receipt.

Atomic file replacement is necessary for corruption resistance but is not, by itself, a concurrency protocol.

---

## 30. Historical Execution and Lost Evidence

If Unreal completed a job but trustworthy execution evidence was lost before durable attestation, Atlas MUST prefer an explicit loss/uncertainty outcome over manufacturing a successful execution claim.

A file that merely looks correct is not sufficient to reconstruct `ENGINE_LIVE` or `ENGINE_JOURNAL_ATTESTED` evidence.

This is an intentional availability trade-off in favor of provenance correctness.

## 34. Acceptance Criteria

Cross-process recovery is not considered complete until all of the following are true:

1. Durable job records survive Atlas restarts.
2. Unreal execution identity survives through durable engine attestation.
3. Atlas can reconcile a job after Unreal restart without human shepherding in the normal successful case.
4. No duplicate execution occurs for one authorized execution attempt.
5. No ambiguous execution is ever turned into successful evidence.
6. Artifact bytes are independently verified against engine-attested hashes.
7. Output namespaces prevent cross-attempt artifact contamination.
8. Existing authorization boundaries remain intact.
9. Existing Stage 17 receipt/provenance guarantees remain intact.
10. Existing live Stage 17 normal-render proof continues to pass.
11. Negative restart/failure tests demonstrate fail-closed behavior for missing or ambiguous evidence.
12. No second authorization, scheduler, or recovery authority exists inside Unreal.

## 36. Explicit Decisions Against Red-Team Proposals

The following suggestions are **not automatically adopted** merely because a reviewer proposed them:

### 36.1 Deterministic/content-derived `atlas_job_id`

Rejected for v1.

Atlas-generated UUID identity is sufficient because the durable Atlas record is the persistence mechanism. `attempt_ordinal` is the explicit distinguisher for re-authorized attempts.

### 36.2 Receipt dispute/retraction system

Deferred from the initial recovery milestone.

The primary safety objective is to make false receipt issuance unreachable. A dispute/supersession mechanism may be added later as production hardening if the existing receipt lifecycle requires it.

### 36.3 New process supervisor inside Unreal

Rejected.

Process death/liveness supervision must use existing host/process infrastructure. Unreal remains a reactive worker.

### 36.4 Automatic resubmission after uncertainty

Rejected.

Execution uncertainty requires reconciliation or explicit re-authorization.

## 37. Final Invariants

1. A render job may execute only under an existing valid Atlas authorization.
2. Atlas is the sole production/recovery authority.
3. Unreal is never the authorization or scheduling authority.
4. Every execution attempt has one immutable Atlas job identity.
5. Re-authorized attempts receive new attempt identity and isolated output space.
6. Atlas persists the job before transmitting `submit_render`.
7. Submission uncertainty never authorizes a blind retry.
8. At most one Atlas coordinator owns the job store.
9. At most one active MRQ execution may exist for one Atlas job attempt.
10. Unreal MUST durably witness acceptance before MRQ dispatch.
11. Unreal MUST durably witness terminal completion through the terminalization path.
12. Terminal jobs may never regress.
13. Missing or unreadable journal state is unknown, not absence.
14. Ambiguous identity always fails closed.
15. Atlas never synthesizes Unreal terminal-success flags.
16. Artifact existence alone is never proof of execution.
17. Every accepted artifact must belong to a job-scoped namespace.
18. Every terminal artifact set requires engine-attested file identity/hash data.
19. Atlas independently verifies file bytes against engine-attested hashes.
20. Artifact completeness must be format-valid, not merely non-empty.
21. Modification time is never sufficient for artifact attribution.
22. Every verified evidence record must preserve execution identity/source class.
23. Receipt issuance requires independently verified evidence.
24. A receipt is create-if-absent and cannot be silently replaced.
25. Durable records are never authoritative over an existing valid receipt.
26. Recovery cannot silently mutate the authorized production plan.
27. New execution after restart requires the existing authorization path.
28. No model may supply or alter recovery authority-bearing values.
29. Recovery waiting is bounded by explicit deadlines.
30. Recovery ambiguity consumes safety budget; temporary transport absence does not become execution failure by itself.
31. Quarantine is non-destructive.
32. Python and C++ share one versioned, language-neutral wire contract.
33. Old/incompatible engine binaries cannot receive recovery-tracked submissions.
34. Recovery is valid only when Atlas and Unreal have a verified shared filesystem view for disk reconciliation.
35. A successful Stage 17 provenance result may never be produced from transport ACKs or filesystem coincidence alone.
36. If trustworthy engine execution evidence did not survive, Atlas must prefer an explicit loss/uncertainty outcome over inventing execution truth.

## 38. Implementation Gate

Hermes MAY begin implementation only after confirming that this document is the authoritative recovery specification and that no higher-priority Atlas contract contradicts it.

Implementation MUST proceed milestone-by-milestone.

At each milestone Hermes MUST:

- inspect current mainline code before changing it;

- maintain Python/C++ language-neutral contracts;
- run deterministic tests appropriate to the milestone;
- avoid action-runner/workflow tests unless explicitly authorized;
- avoid unrelated Blender or Atlas Live changes;
- not create a second authority path;
