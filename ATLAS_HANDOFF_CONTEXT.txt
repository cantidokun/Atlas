Date: August 16, 2026
Current Milestone: Conditional Execution + Generic Verification Architecture Proven; Next: Generalize Autonomous Task Control

============================================================
1. PROJECT
============================================================

Atlas is an AI-assisted sports virtual production and digital-twin platform.

Blender is the first proven execution environment. Unreal Engine is a planned
complementary production environment. The long-term goal is a production suite
in which specialized AI agents can understand captured sports footage, reason
about environments and assets, plan production changes, execute operations,
and independently verify the resulting state.

Core control principle:

Qwen / AI agents
    -> understand, reason, propose

Python / Atlas control layer
    -> validate schemas, authorize, execute, track state, verify, recover

Production tools
    -> Blender now; Unreal and other specialized tools later

Independent verification
    -> confirm what actually happened before completion

The architecture must remain environment-agnostic above the production-tool
adapter boundary. Goalpost behavior is a test case, not the generic design.

3. CORE FILES AND RESPONSIBILITIES
============================================================

Legacy/proven controller layer:

controller_state.py
- Tracks BEFORE, TARGET, WRITE, AFTER, COMPLETE.
- Calculates target positions from measured evidence.

controller_runtime.py
- Executes exactly one mandatory controller action at a time.
- Does not delegate mandatory ordering to Qwen.

controller_bridge.py
- Connects controller state to the existing agent.
- Hydrates BEFORE state from evidence.

controller_execution_adapter.py
- Mirrors controller-owned results into normal tool history/evidence.

controller_integration.py
- Integration boundary between agent and controller.

run_agent_with_controller.py
- Live compatibility entrypoint.

controller_finalization.py
- Builds deterministic final reports from verified evidence.

Generic planning layer:

action_plan.py
- `ActionSpec`: one ordered authorized action.
- `ActionPlan`: exposes next action, records results, advances only after success,
  blocks on required failure, reports completion, snapshots state.

evidence_plan.py
- Ordered evidence requests, completion, reuse, and blocking failures.

planning/planning_orchestrator.py
- `PlanningOrchestrator`: generic evidence -> action state machine.
- `ConditionalPlanningOrchestrator`: evidence -> target evaluation -> conditional
  action -> verification -> completion, with deterministic future/recovery gates.
- Actions remain blocked until evidence and target-state evaluation are complete.
- Exposes explicit phases including EVIDENCE, TARGET_EVALUATION, ACTION,
  VERIFICATION, COMPLETE, BLOCKED, and recovery/replan states.

planning/target_state.py
- Named `StateInvariant` requirements and `TargetStateEvaluator`.
- Produces explicit satisfied/failed invariant results and snapshots.

planning/verification_plan.py
- Generic post-action verification primitive.
- A write result is never treated as proof of final state.
- Requires independent evidence evaluated against the target-state evaluator.
- Failed verification remains blocked/fails closed.

planning/future_generator.py
- `DeterministicFutureGenerator` creates the only legal execution future implied
  by an already-authorized action list and resolved target state.
- No model reasoning or tool execution occurs here.
- Conditional futures explicitly branch into SKIP_WRITES or authorized ACTIONs,
  then VERIFICATION and COMPLETE.

planning/future_execution.py
- `FutureExecutionController` owns the execution cursor.
- Prevents skipping/reordering/inventing steps.
- Uses a plan digest to detect mutation.
- Only successful actions advance the cursor.
- Verification must be independently positive before COMPLETE can be finalized.

planning/future_recovery.py
- `FutureRecoveryGate` handles failed deterministic futures.
- No automatic retry.
- Action failures require fresh authoritative evidence before recovery planning.
- Verification failures require a new authorized plan.
- Terminal/ambiguous failures fail closed.

planning/replan_authorization.py
- `ReplanAuthorization` is an immutable authorization receipt binding fresh
  evidence and the exact replacement action list by digest.
- Replacement actions must match the issued authorization before installation.

Authorization/audit/runtime bridge:

task_plan_authorization.py
- Explicit authorization boundary for proposed plans and write tools.

audit_trail.py
- Records proposal, evidence, authorization, execution, and verification order.

qwen_planning_runtime.py
- Parses/validates Qwen structured plans.

live_qwen_planning_loop.py
- Live Qwen -> Python structured planning bridge.
- Qwen proposes structured evidence/actions; Python validates and controls the
  execution boundary.
- Current conditional harness supports `--case already-correct` and
  `--case incorrect` using deterministic test fixtures.

live_qwen_conditional_loop.py
- Live conditional Blender harness.
- Uses `CORRECT_FILE = goalpost_test_CONDITIONAL_CORRECT.blend` and
  `INCORRECT_FILE = goalpost_test_CONDITIONAL_INCORRECT.blend`.
- Target left post = [0.0, 5.233, 0.0].
- Target right post = [0.0, -5.233, 0.0].
- Target midpoint = [0.0, 0.0, 0.0].
- Target distance = 10.466.
- Allowed tools are restricted to `inspect_object_relationship` and
  `move_object`.
- Uses generic `ConditionalPlanningOrchestrator` and generic `VerificationPlan`.

============================================================
8. CONTROLLED FAILURE / RECOVERY — PASS
============================================================

The controlled recovery architecture is proven.

A simulated/realized write failure produces a fail-closed state requiring:
- fresh authoritative evidence
- explicit recovery classification
- a replacement plan where appropriate
- independent re-authorization

Automatic retry is prohibited.

`FutureRecoveryGate.authorize_retry()` intentionally raises rather than
silently repeating a potentially stale or partially applied action.

11. CURRENT KNOWN ISSUES / BOUNDARIES
============================================================

1. The Qwen model remains a proposal source, not an execution authority.
   Malformed or semantically invented tool arguments must be rejected before
   any production executor is called.

2. The live conditional harness currently proves the architecture using the
   goalpost Blender relationship. It is not yet a general-purpose autonomous
   production task runner.

3. The deterministic future is derived from an already-authorized action plan.
   Atlas has not yet generalized autonomous multi-task planning across arbitrary
   production tools.

4. Recovery/replanning primitives exist, but broader live end-to-end recovery
   against arbitrary production failures still needs dedicated integration
   coverage.

5. The local live runtime uses Ollama/qwen3:8b and Blender 4.4. CI tests are
   offline Python tests; CI does not replace the local Blender/Qwen live tests.

6. The current live workflow still requires the local runner/test harness to be
   invoked explicitly. The architecture is moving toward autonomous execution,
   but full unattended local execution is not yet the milestone to declare.

13. EXACT NEXT STEPS
============================================================

NEXT STEP 1 — Generalize the verified conditional architecture.

Extract the goalpost-specific assumptions from the live conditional harness
while preserving the proven generic primitives:

Task
 -> structured evidence requirements
 -> authoritative evidence
 -> explicit target-state evaluator
 -> conditional decision
 -> deterministic future
 -> authorized action sequence if needed
 -> independent verification
 -> completion

The next implementation should make this reusable for a second non-goalpost
production task rather than adding another special case to the goalpost code.

NEXT STEP 2 — Strengthen tool argument/schema validation.

Before any executor call, validate:
- tool name
- exact required argument names
- argument types
- allowed values/ranges where applicable
- action ordering requirements
- authorization scope

A malformed Qwen plan must fail at the planning boundary.

NEXT STEP 3 — Add generic conditional regression coverage.

Cover at minimum:
- already satisfied -> zero actions executed
- unsatisfied -> all authorized actions execute in order
- successful action -> verification still required
- failed verification -> BLOCKED
- action failure -> recovery gate
- mutated deterministic future -> integrity failure
- unauthorized replan -> rejected
- authorized replan matching fresh evidence -> accepted

NEXT STEP 4 — Prove the architecture on a second production task.

Use a task with different target invariants and a different action shape so the
architecture cannot accidentally remain goalpost-specific.

NEXT STEP 5 — Only after that, begin Stage 9 broader autonomous task control.

Stage 9 should focus on safely composing evidence, target-state, action,
verification, and recovery primitives into a reusable task runtime rather than
letting Qwen directly control tools.

15. DEVELOPMENT RULES
============================================================

Do not rewrite the entire agent.
Do not remove the evidence ledger.
Do not remove independent post-write verification.
Do not make goalpost behavior the generic architecture.
Do not add tools without proving a real capability gap.
Do not let a successful production state depend on a perfect Qwen final answer.
Do not allow an action plan to execute without explicit authorization.
Do not allow Qwen to bypass Python-owned execution state.
Do not allow automatic retry after failed writes.
Keep Blender/Unreal-specific behavior behind appropriate adapter/tool boundaries.
Preserve working components and improve incrementally.
Keep README.md, ATLAS_HANDOFF_CONTEXT.txt, and DEVELOPMENT_LOG.md synchronized
with verified milestones and test results.

17. HANDOFF SUMMARY
============================================================

Atlas has moved beyond the question "can Python reliably control one known
modification?"

The current proven answer is:

Atlas can accept a structured Qwen proposal, validate it, acquire authoritative
evidence, determine whether the requested state is already satisfied, skip an
unnecessary write, or execute an explicitly authorized deterministic action
sequence, and independently verify the resulting state before completion.

The next architectural challenge is generalization: prove that this control
loop is reusable across different production tasks without embedding task-
specific assumptions into the generic planning layer.

Core principle remains:

Reason with Qwen.
Control with Python.
Measure with production tools.
Verify independently.
Recover conservatively.
