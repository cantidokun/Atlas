6. FACTUALITY RULES
============================================================

Atlas currently uses 46 factuality rules.

Core principles:

1. Only state facts supported by tool results or user
   instructions.

2. Never invent measurements, object types, settings,
   capabilities, or scene information.

3. Distinguish measured facts from inference and
   recommendations.

4. If information is unavailable, explicitly state that it
   is unavailable or unestablished.

5. Prefer tools over guessing.

6. After modifications, perform separate verification.

7. Do not claim that nothing else changed unless evidence
   supports that claim.

8. Distinguish measured data from inference.

9. Do not recommend optimization merely because geometry exists.

10. When evidence is insufficient, state what information
    is needed.

11. Never recommend a change merely because it is common
    3D workflow practice.

12. Do not describe materials, modifiers, geometry,
    or object characteristics unless a tool provides them.

13. Do not assume more geometry/materials/modifiers are
    inherently better.

14. When no problem is demonstrated, say so.

15. Never use assumptions to fill missing tool information.

16. Do not claim an object was not modified unless execution
    or verification evidence supports that statement.

17-43. Additional rules reinforce:
    - evidence-first reasoning
    - tool capability awareness
    - no unsupported inference
    - no unsupported recommendations
    - correct handling of unavailable information
    - avoiding redundant tool calls
    - distinguishing evidence gaps from demonstrated problems
    - respecting documented tool capabilities
    - avoiding external standards without authorization

44. Successful tool results are recorded in the evidence
    ledger and must be treated as established evidence.

45. Before recommending another inspection, check the evidence
    ledger and do not repeat an inspection solely to obtain
    information already present.

46. Do not introduce real-world standards, specifications,
    tolerances, or thresholds unless explicitly provided by
    the user, returned by a tool, or obtained from an explicitly
    requested external source.

17. GENERAL EVIDENCE PLANNER PRINCIPLE
============================================================

The planner should not simply execute every tool that seems
potentially useful.

It should acquire evidence only when:

1. The current task requires the information.
2. The information is not already in the evidence ledger.
3. An available tool can acquire it.

The desired cycle is:

Evidence gap
    ↓
Check existing capabilities
    ↓
Can an existing tool resolve it?
    ↓
YES
    ↓
Acquire evidence
    ↓
Add to ledger
    ↓
Reason again

If no existing tool can resolve the evidence gap:

Evidence gap
    ↓
Capability unavailable
    ↓
Identify actual capability gap
    ↓
Only then consider adding a new tool

------------------------------------------------------------

A controller-level reasoning/tool loop guard was added.

Current limits:

MAX_REASONING_STEPS = 8
MAX_REPEATED_REASONING = 3
MAX_REASONING_SIMILARITY = 0.92

- prevent Qwen from consuming excessive inference time while repeating

pattern around the availability of the Blender filename.

35. SAFE ACTION BOUNDARY — NEXT MILESTONE
------------------------------------------------------------

The next major test should distinguish three separate states:

1. ANALYSIS
   Atlas determines whether a change is required.

2. PROPOSAL
   Atlas calculates and states the exact modification that would be
   performed.

3. AUTHORIZATION / EXECUTION
   Atlas is explicitly permitted to perform a Blender write operation.

The system must NOT collapse these states.

Desired safety boundary:

Requirement
    ↓
Evidence
    ↓
Decision
    ↓
Proposed modification
    ↓
Explicit user authorization
    ↓
Write tool
    ↓
Independent verification
    ↓
Final response

A proposed modification must not itself be treated as authorization.

    INITIAL / MEASURED STATE

and:

    FINAL / VERIFIED STATE

The validator repeatedly required the original measured midpoint:

    [0.0, 0.138, 0.0]

even after the modification had produced the final midpoint:

    [0.0, 0.0, 0.0]

It also required explicit reporting of:

    - measured initial positions
    - measured initial midpoint
    - target positions
    - positional adjustment
    - final verified positions
    - final verified midpoint

Therefore, Atlas should not use ambiguous wording such as:

    "current position"

when multiple temporal states exist.

Use explicit state labels:

    INITIAL MEASURED STATE
    CALCULATED TARGET STATE
    FINAL VERIFIED STATE

This should become part of the completion-validation design.
